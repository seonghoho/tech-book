# HTTP 캐시 정리: 휴리스틱 캐시, no-cache와 no-store, ETag까지

배포를 했는데 일부 사용자 화면만 예전 동작이 남아 있었다. 원인은 캐시 헤더가 없는 정적 JS였다. 그 과정은 [배포했는데 사용자 화면은 그대로? 정적 JS 캐시 전략 4가지 비교](/posts/web-performance/static-js-cache-strategy)에 정리했다.

이 글은 그때 헷갈렸던 개념을 따로 모은 학습 노트다. 개념마다 **한 줄 정의 → 예시 → 자주 하는 오해** 순서로 정리했다.

---

## 0. 먼저 큰 그림: 캐시는 두 가지 질문에 답한다

브라우저가 저장해 둔 응답(캐시)을 다시 쓸지 정할 때 던지는 질문은 두 개뿐이다.

1. **아직 신선한가? (freshness)** 서버에 묻지 않고 그냥 써도 되는 기간인가.
2. **신선하지 않다면, 아직 유효한가? (validation)** 서버에 "이거 바뀌었어?" 하고 물어서 안 바뀌었으면 계속 쓴다.

```text
캐시에 저장본 있음?
 ├─ 없음 → 서버에서 새로 받기 (200)
 └─ 있음 → 신선한가?
            ├─ 예 → 서버에 묻지 않고 바로 사용 (요청 자체가 없음)
            └─ 아니오 → 서버에 재검증 요청 (If-None-Match / If-Modified-Since)
                         ├─ 안 바뀜 → 304 Not Modified, 본문 없음 → 저장본 사용
                         └─ 바뀜   → 200 + 새 본문 → 저장본 교체
```

`Cache-Control` 의 지시어들은 결국 **1번 신선도 기간을 얼마로 할지**, **2번 재검증을 언제 꼭 해야 하는지**, **애초에 저장해도 되는지**를 정하는 도구다.

---

## 1. 휴리스틱 캐시 (heuristic freshness)

**한 줄 정의:** 서버가 유효 기간을 알려 주지 않으면, 브라우저가 `Last-Modified` 를 보고 유효 기간을 **스스로 추측**하는 것.

가장 흔한 오해는 "`Cache-Control` 이 없으면 캐시를 안 한다"이다. 실제로는 반대다. 아무 말이 없으면 **브라우저가 알아서 정한다.**

HTTP 캐시 표준(RFC 9111)은 명시적인 유효 기간이 없을 때 캐시가 유효 기간을 추정해도 된다고 허용한다. 흔히 쓰는 값으로 **`Last-Modified` 이후 지난 시간의 10%** 를 예로 든다. Chromium 계열 브라우저도 이 방식을 쓴다.

```text
응답 시각(Date)     : 2026-11-05
Last-Modified       : 2026-08-05   (석 달 전에 마지막으로 바뀐 파일)
지난 시간           : 약 92일
휴리스틱 유효 기간  : 92일 × 10% ≈ 9일
→ 앞으로 약 9일 동안은 서버에 묻지 않고 저장본을 쓴다
```

**왜 이게 문제가 되나**

- 오래 안 바뀐 파일일수록 유효 기간이 길어진다. 그런데 바로 그런 파일을 오랜만에 고쳐 배포하면, 사용자들은 며칠씩 옛 파일을 쓴다.
- 유효 기간을 서버가 아니라 **브라우저가 정한다.** 그래서 사용자마다, 언제 마지막으로 받았는지에 따라 결과가 다르다. 재현이 어렵고 "내 폰에서만 그래요"가 된다.

**자주 하는 오해**

- ❌ "헤더를 안 주면 매번 새로 받겠지" → ⭕ 브라우저가 기간을 추측해서 캐시한다.
- ❌ "`Last-Modified` 는 재검증용일 뿐" → ⭕ 휴리스틱 계산의 재료로도 쓰인다.

**결론:** 바뀔 수 있는 파일에는 **반드시 `Cache-Control` 을 명시**한다. 판단을 브라우저에 맡기지 않는다.

## 2. `no-cache` 와 `no-store`: 이름 때문에 가장 많이 헷갈리는 둘

| 지시어 | 저장 | 쓸 때 | 한 줄 요약 |
|---|---|---|---|
| `no-cache` | **저장한다** | **매번 서버에 확인(재검증)한 뒤** 사용 | "저장은 해도 되는데, 쓰기 전에 꼭 물어봐" |
| `no-store` | **저장하지 않는다** | 매번 처음부터 새로 받음 | "아예 남기지 마" |

이름만 보면 `no-cache` 가 "캐시하지 마"처럼 읽힌다. 하지만 실제 의미는 **"확인 없이 쓰지 마"**다.

### `no-cache` 의 실제 흐름

```text
1) 첫 요청
GET /libs/viewer.js
← 200 OK
   Cache-Control: no-cache
   ETag: "44de-4DUQvTkqi0CL+aQVy4mUNEuQvwI"
   (본문 17,630 B, brotli)

2) 다음에 쓸 때 (저장본 있음 → 바로 쓰지 않고 확인)
GET /libs/viewer.js
If-None-Match: "44de-4DUQvTkqi0CL+aQVy4mUNEuQvwI"
← 304 Not Modified      (본문 0 B → 저장본 그대로 사용)
```

파일이 안 바뀌었으면 **요청은 가지만 본문은 오지 않는다.** 그래서 "항상 최신 + 데이터 절약"이 동시에 된다. 대신 매번 왕복 시간(RTT)이 든다.

### `no-store` 가 맞는 곳

- 개인정보가 담긴 응답, 결제·계좌 정보, 한 번 보고 버려야 하는 토큰 응답
- 공용 PC에 흔적이 남으면 안 되는 페이지

정적 JS·CSS에 `no-store` 를 쓰면 **매번 전체를 다시 받는다.** 최신성만 원한다면 `no-cache` 로 충분하다.

**자주 하는 오해**

- ❌ "`no-cache` = 캐시 안 함" → ⭕ 저장은 하고, 쓸 때마다 재검증한다.
- ❌ "최신을 보장하려면 `no-store`" → ⭕ `no-cache` 로도 최신이 보장된다. `no-store` 는 저장 자체가 문제일 때 쓴다.

## 3. 신선도를 정하는 지시어: `max-age`, `immutable`, `must-revalidate`

| 지시어 | 의미 |
|---|---|
| `max-age=N` | 받은 뒤 N초 동안은 서버에 묻지 않고 쓴다 |
| `max-age=0` | 받자마자 신선하지 않음. 쓸 때 재검증해야 한다 |
| `must-revalidate` | 신선도가 지나면 **반드시** 재검증한다. 서버에 연결이 안 되더라도 지난 저장본을 쓰지 않는다 |
| `immutable` | 유효 기간 안에는 사용자가 새로고침해도 재검증하지 않는다. 내용이 절대 안 바뀐다는 선언 |
| `public` / `private` | 공유 캐시(CDN, 프록시)에 저장해도 되는지. 사용자별 응답은 `private` |

`no-cache` 는 `max-age=0, must-revalidate` 와 거의 같은 효과다. 매번 재검증하고, 지난 저장본을 함부로 쓰지 않는다.

### 해시 파일명 + `immutable`: 가장 이상적인 조합

Nuxt·Vite가 만드는 파일은 이렇게 나간다.

```text
GET /_nuxt/D255EP6g.js
← cache-control: public, max-age=31536000, immutable
```

1년 동안 묻지도 않는데 문제가 없는 이유는 **파일 이름에 내용 해시가 들어 있기 때문**이다. 내용이 바뀌면 이름이 `D255EP6g` → `Bx91Kq2a` 처럼 바뀐다. HTML이 새 이름을 가리키니 브라우저는 새 파일을 받는다. 옛 이름의 파일은 아무도 부르지 않아서 캐시에 남아 있어도 해가 없다.

이 방식을 흔히 **cache busting(캐시 무효화)** 이라고 부른다. "같은 주소의 내용을 바꾸는" 대신 "**내용이 바뀌면 주소를 바꾸는**" 방식이다.

**주소를 고정할 수밖에 없는 파일이라면?** 레거시 스크립트, `favicon.ico`, `robots.txt` 처럼 이름을 못 바꾸는 파일은 `no-cache` + ETag 재검증이 현실적인 선택이다.

## 4. 재검증의 열쇠: `ETag` 와 `Last-Modified`

| 응답 헤더 (서버 → 브라우저) | 재검증 요청 헤더 (브라우저 → 서버) | 비교 기준 |
|---|---|---|
| `ETag: "44de-4DUQ..."` | `If-None-Match: "44de-4DUQ..."` | 내용 식별자가 같은가 |
| `Last-Modified: Thu, 05 Nov 2026 01:06:00 GMT` | `If-Modified-Since: Thu, 05 Nov 2026 01:06:00 GMT` | 그 시각 이후 바뀌었나 |

- 둘 다 있으면 **ETag 가 우선**한다.
- `Last-Modified` 는 초 단위라 1초 안에 두 번 바뀌면 구분하지 못한다. 배포할 때마다 파일 시각이 갱신되면 내용이 같아도 "바뀜"으로 판단될 수 있다.
- ETag 를 **내용 기반으로 만드는 서버**라면, 배포해서 파일 시각이 바뀌어도 내용이 같으면 ETag 도 같다. 그래서 304가 나온다.

실제로 확인한 예: 운영 서버와 로컬 빌드에서 같은 `viewer.js` 의 ETag 가 `"14f0c-z1IIp5..."` 로 같았다. 앞부분 `14f0c` 는 파일 크기(16진수, 85,772 B)이고, 뒷부분은 내용 해시다.

**강한 ETag와 약한 ETag**

- `"abc"`: 강한 ETag. 바이트 단위로 같다.
- `W/"abc"`: 약한 ETag. 의미상 같다. 압축 방식이 달라 바이트는 달라도 같은 문서로 본다.

**자주 하는 오해**

- ❌ "304면 요청이 안 간 것" → ⭕ 요청은 갔고, 본문만 안 온 것이다. 요청 자체가 없는 건 신선도 기간 안에서 저장본을 바로 쓴 경우다.

## 5. `Vary`: 같은 주소, 다른 응답

**한 줄 정의:** "이 응답은 요청의 **이 헤더 값에 따라 달라지니**, 캐시할 때 그 값까지 키로 묶어라."

압축을 켜면 같은 `/libs/viewer.js` 라도 응답이 세 가지가 된다.

```text
Accept-Encoding: (없음)    → 원본 85,772 B
Accept-Encoding: gzip      → gzip 20,763 B
Accept-Encoding: br, gzip  → brotli 17,630 B
```

이때 `Vary: Accept-Encoding` 이 없으면 중간 캐시(CDN, 프록시)가 brotli 응답을 저장해 뒀다가, brotli 를 모르는 클라이언트에게 그대로 줄 수 있다. 그러면 깨진 파일이 된다. `Vary` 가 있으면 캐시가 `Accept-Encoding` 값마다 따로 저장한다.

Nitro 의 `compressPublicAssets` 는 압축본을 내려줄 때 `Vary: Accept-Encoding` 을 자동으로 붙인다. 응답 헤더로 확인했다.

## 6. 함정: 캐시 정책을 바꿔도 이미 받은 것은 바뀌지 않는다

이번에 가장 크게 배운 부분이다.

`Cache-Control` 은 **응답에 붙어서 그 응답의 운명을 정하는 헤더**다. 서버 설정을 바꿔도 이미 사용자 기기에 저장된 응답에는 옛 규칙(또는 휴리스틱)이 그대로 남는다.

```text
[과거] /libs/viewer.js 를 Cache-Control 없이 받음 → 휴리스틱으로 약 9일 신선
[오늘] 서버를 no-cache 로 변경
[내일] 사용자 → 아직 9일 안 지남 → 서버에 묻지 않고 옛 파일 사용
        → 새 헤더가 있다는 것도 모름
```

서버가 이미 저장된 캐시를 지울 방법은 사실상 없다. `Clear-Site-Data` 헤더가 있긴 하지만, 그 헤더를 받으려면 결국 요청이 와야 한다. 그래서 해결책은 하나다.

> **주소를 바꾼다.** 캐시는 URL 단위로 저장되므로, 새 주소에는 저장본이 없다.

이번에는 스크립트 주소에 `?v=2` 를 한 번 붙여 해결했다. 이후 변경은 `no-cache` 재검증이 처리하므로 번호를 계속 올릴 필요는 없다.

**교훈:** 캐시 정책은 처음부터 명시해 두는 게 가장 싸다. 나중에 바꿀 때는 "앞으로 받을 것"과 "이미 받은 것"을 따로 계획한다.

## 7. 개발자 도구로 직접 확인하기

크롬 개발자 도구 Network 탭에서 각 요청의 Size / Status 열을 보면 캐시 동작을 바로 알 수 있다.

| 표시 | 의미 |
|---|---|
| `(memory cache)` / `(disk cache)` | 신선도 기간 안이라 **요청 없이** 저장본 사용 |
| Status `304` | 재검증 요청을 보냈고, 안 바뀌어서 본문 없이 저장본 사용 |
| Status `200` + 실제 크기 | 새로 받음 |

- **Disable cache** 체크박스: 개발자 도구가 열려 있는 동안 캐시를 끈다. 켜 두고 확인하면 실제 사용자 상황과 달라진다.
- **새로고침 종류:** 일반 새로고침, 강력 새로고침(캐시 무시), 주소창에서 엔터는 각각 캐시를 다르게 다룬다. 사용자 상황을 재현하려면 주소창에서 다시 열기나 링크 클릭이 가깝다.

터미널에서는 `curl` 로 헤더만 볼 수 있다.

```bash
curl -sI -H 'Accept-Encoding: br, gzip' 'https://example.com/libs/viewer.js?v=2'
```

## 8. 한 장 요약

| 상황 | 추천 |
|---|---|
| 해시 파일명이 붙는 빌드 결과물 (`/_nuxt/`, `/assets/`) | `public, max-age=31536000, immutable` |
| 주소가 고정된 정적 파일 (레거시 스크립트 등) | `no-cache` + ETag 재검증 |
| HTML 문서 | `no-cache` (또는 짧은 `max-age`). 문서가 최신이어야 해시 파일을 가리킬 수 있다 |
| 개인정보·민감 응답 | `no-store` (공유 캐시가 있으면 `private` 도) |
| 아무것도 안 줌 | ❌ 휴리스틱 캐시에 맡기게 된다 |

## 9. 스스로 점검하기

1. `Cache-Control` 도 `Expires` 도 없고 `Last-Modified` 가 30일 전인 파일은, 받은 뒤 대략 얼마 동안 재검증 없이 쓰일 수 있을까?
2. `no-cache` 를 준 파일을 다시 열었는데 Network 탭에 304가 보였다. 이 요청에서 내려받은 본문 크기는?
3. 비밀번호 재설정 링크를 담은 응답에는 `no-cache` 와 `no-store` 중 무엇이 맞을까?
4. brotli 압축을 켰는데 `Vary: Accept-Encoding` 이 빠졌다. 어떤 문제가 생길 수 있을까?
5. 오늘 서버 설정을 `no-cache` 로 바꿨다. 어제 이 파일을 받은 사용자는 언제 새 파일을 받게 될까? 바로 받게 하려면?

### 답

1. 30일의 10%인 약 3일. 브라우저마다 다를 수 있다.
2. 0바이트. 헤더만 오고 저장본을 쓴다.
3. `no-store`. 기기에 남으면 안 된다.
4. 중간 캐시가 brotli 응답을 brotli 를 모르는 클라이언트에게 줄 수 있다.
5. 어제 받은 응답의 휴리스틱 유효 기간이 끝나야 서버에 다시 묻는다. 바로 받게 하려면 주소를 바꾼다(`?v=2` 등).
