# BFF PoC에서 만난 문제들

프론트엔드 BFF 연재의 3편이자 마지막 편입니다. [1편](/posts/frontend-bff/bff-security-review)에서는 BFF로 무엇이 달라지는지, [2편](/posts/frontend-bff/bff-poc-structure)에서는 사이드 프로젝트에 넣은 구조를 적었습니다.

이번 편은 PoC를 운영하며 만난 문제와, 각각을 어떻게 고쳤는지입니다. 사내 서비스에서 났다면 바로 장애로 이어졌을 문제들이라 사내 적용 전에 확인할 항목으로 정리했습니다.

## 만료 토큰에 500이 돌아온 문제

두 사이드 프로젝트 모두에서 났고, 영향이 가장 컸습니다.

**증상.** access token의 수명은 1시간입니다. 로그인하고 1시간이 지난 사용자는 모든 API에서 500을 받았습니다. 토큰이 필요 없는 장소 목록 같은 공개 API도 마찬가지였습니다. 화면은 500을 일시적인 오류로 보고 재시도 버튼을 보여 줬지만, 눌러도 계속 500이었습니다. 로그인한 사용자에게는 한 시간 뒤면 서비스가 멈추는 셈이었습니다.

**원인.** 백엔드 게이트웨이가 토큰 만료 예외를 처리하지 않아서, 401이 아니라 기본 오류 처리로 넘어가 500이 나갔습니다. BFF는 401일 때만 재발급하도록 만들었기 때문에, 500에는 재발급이 일어나지 않았습니다. 토큰이 영원히 갱신되지 않았습니다.

2편에서 적은 "401이면 한 번 재발급하고 다시 보낸다"는 구조는, 백엔드가 만료 토큰에 401을 준다는 전제 위에 있었습니다. 그 전제가 틀리자 BFF의 재발급이 통째로 동작하지 않았습니다.

**두 프로젝트는 이 문제를 다르게 고쳤습니다.**

| | 첫 번째 프로젝트 | 두 번째 프로젝트 |
|---|---|---|
| 고친 곳 | 프론트엔드 BFF | 백엔드 게이트웨이 |
| 방법 | 요청을 보내기 전에 토큰 만료를 직접 확인해 미리 재발급 | JWT 예외를 401·503 응답으로 바꾸는 핸들러 추가 |
| 성격 | 백엔드를 바로 고칠 수 없을 때의 우회 | 원인을 없앤 수정 |

첫 번째 프로젝트는 BFF에서 막았습니다. 만료된 토큰을 아예 보내지 않으면 500을 받을 일이 없다는 접근입니다.

```ts
// app/api/bff/[...path]/route.ts (첫 번째 프로젝트, 단순화)
let session = await getSession()

// 토큰의 exp를 읽어 만료(임박)면 요청 전에 재발급한다
if (session && isAccessTokenExpired(session.accessToken, Date.now())) {
  const next = await refreshSessionOnce(session) // 동시 요청이 몰려도 재발급은 한 번
  if (next) {
    await setSession(next)
    session = next
  } else {
    // 재발급도 실패하면 세션을 지우고 토큰 없이 보낸다
    // 공개 API는 200, 로그인이 필요한 API는 백엔드가 401
    await clearSession()
    session = null
  }
}
```

재발급까지 실패하면 오류를 내지 않고 로그인하지 않은 상태로 보냅니다. 그래야 공개 API는 계속 보이고, 로그인이 필요한 API만 401로 로그인 화면에 보낼 수 있습니다. 만료된 세션 쿠키로 요청했을 때 500이던 응답이 200으로 바뀐 것을 테스트로 확인했습니다.

두 번째 프로젝트는 백엔드 게이트웨이에 JWT 예외 핸들러를 추가했습니다. 만료, 형식 오류, 서명 오류, 폐기된 토큰은 401로, 블랙리스트 조회 실패는 503으로 공통 응답 형식에 담아 내려줍니다. 백엔드가 401을 주니 BFF에 원래 있던 재발급 로직이 그대로 동작했습니다.

같은 원인을 한쪽은 프론트엔드에서, 한쪽은 백엔드에서 고친 셈입니다. 첫 번째 방식은 백엔드와 일정을 맞추지 않아도 바로 막을 수 있지만, 프론트엔드가 토큰 내용을 직접 해석하는 코드가 늘어납니다. 두 번째 방식은 백엔드 수정이 필요하지만, BFF는 401만 믿으면 됩니다. 사내에 적용한다면 두 번째 방식을 기본으로 하고, 백엔드 수정이 늦어질 때 첫 번째 방식을 임시로 쓰는 쪽으로 검토할 생각입니다.

## 로그인 실패가 두 번씩 세어진 문제

두 번째 프로젝트에서 난 문제입니다.

**증상.** 세션이 남아 있는 상태에서 비밀번호를 틀리면 실패가 2회로 세어졌습니다. 만료된 세션을 가진 채 다시 로그인하거나, 다른 계정으로 로그인할 때가 그런 상태입니다. 그래서 계정 잠금이 원래 횟수의 절반 만에 걸렸습니다.

**원인.** BFF의 재시도 조건이 "세션이 있고, 재발급 요청 자체가 아니면"뿐이었습니다. 그런데 로그인 실패도 401로 옵니다. 그래서 로그인 401 → 토큰 재발급 → 로그인 재시도 → 다시 401 순서로, 틀린 비밀번호가 백엔드에 두 번 들어갔습니다.

**수정.** 로그인 진입 경로를 재시도 대상에서 뺐습니다.

```ts
// 일반 로그인, 소셜 로그인 콜백
const AUTH_ENTRY_PATTERN = /^auth\/(login|[^/]+\/login)$/

export function isAuthEntryPath(path: string): boolean {
  const withoutQuery = path.split('?')[0] ?? ''
  return AUTH_ENTRY_PATTERN.test(withoutQuery.replace(/^\/+/, ''))
}

// 재시도 조건에 추가
if (
  result.status === 401 &&
  session !== null &&
  !isReissuePath(path) &&
  !isAuthEntryPath(path) // 로그인 실패는 재발급으로 복구되지 않는다
) {
  // 재발급 후 재시도
}
```

토큰이 만료된 401은 재발급으로 복구되지만, 비밀번호가 틀린 401은 몇 번을 다시 보내도 실패하고 실패 횟수만 쌓입니다. BFF가 인증 흐름 한가운데에서 자동으로 재시도하기 때문에, 어떤 요청을 재시도하면 안 되는지도 BFF가 알고 있어야 했습니다.

## 소셜 로그인이 막힐 뻔한 문제

이것도 두 번째 프로젝트입니다. 백엔드가 소셜 로그인 위조를 막으려고, 로그인 시작 때 `state` 값을 쿠키로 내려주고 콜백에서 대조하도록 바꿨습니다.

문제는 BFF가 게이트웨이 쿠키를 전부 넘기지 않고, refresh token만 골라서 주고받는 구조였다는 점입니다. 새로 생긴 state 쿠키는 BFF에서 버려졌습니다. 쿠키를 그대로 브라우저에 넘길 수도 없었습니다. 게이트웨이 쿠키의 경로는 `/api/v1/auth`인데 브라우저가 보는 경로는 `/api/bff/auth/...`라서, 브라우저가 그 쿠키를 다시 보내지 않습니다. 백엔드 변경만 먼저 배포됐다면 소셜 로그인이 전부 실패했을 겁니다.

BFF가 state를 중계하도록 고쳤습니다.

1. 로그인 시작 응답의 Set-Cookie에서 state 값을 꺼낸다
2. 전용 쿠키에 암호화해 브라우저에 둔다
3. 콜백 요청 때 그 값을 Cookie 헤더로 게이트웨이에 다시 실어 보내고, 끝나면 지운다

기존 세션 쿠키에 넣지 않고 전용 쿠키를 둔 이유는, state를 받는 시점이 아직 로그인 전이라 세션이 없기 때문입니다. 이 수정은 백엔드 변경과 같이 배포해야 했습니다.

BFF가 쿠키를 골라서 다루는 구조는 1편에서 말한 보안상 장점이지만, 반대로 백엔드가 쿠키를 하나 추가할 때마다 BFF도 같이 바뀌어야 한다는 뜻이기도 했습니다.

## 본문을 읽는 방식 때문에 깨진 것

나머지 두 문제는 BFF가 요청과 응답의 본문을 어떻게 다루는지에서 나왔습니다. 둘 다 두 번째 프로젝트이고, 출시 전에 발견했습니다.

- **multipart 업로드.** BFF가 요청 본문을 문자열(`request.text()`)로 읽고 Content-Type을 JSON으로 고정하고 있었습니다. 파일 업로드는 boundary가 Content-Type 헤더에 있고 본문이 바이너리라 이 방식으로는 깨집니다. 원본 Content-Type을 그대로 쓰고 본문을 ArrayBuffer로 읽도록 고쳤습니다. 401 재시도 때 같은 본문을 다시 보내야 해서, 스트림이 아니라 버퍼로 들고 있습니다.
- **SSE.** BFF가 게이트웨이 응답 전체를 기다렸다가(`await response.text()`) 넘기고 있어서, AI 일정 생성의 진행 이벤트가 작업이 다 끝난 뒤 한꺼번에 왔습니다. 요청의 `Accept`가 `text/event-stream`이면 별도 경로로 빠져 응답 본문을 그대로 흘려보내게 했습니다. 401 재시도는 스트림이 시작되기 전에만 하고, 브라우저가 연결을 끊으면 게이트웨이 연결도 같이 끊기도록 `request.signal`을 넘겼습니다.

일반 JSON API만 생각하고 만든 프록시라, 파일과 스트림처럼 본문 모양이 다른 요청에서 깨졌습니다.

## 사내 적용 때 확인할 항목

PoC에서 만난 문제를 사내 적용 전에 확인할 항목으로 바꿔 정리했습니다. 사내 서비스는 Nuxt에서 Next.js로 옮기는 통합 마이그레이션과 함께 BFF를 진행하고 있어서, 이 목록을 그 작업에 그대로 가져갈 생각입니다.

- 백엔드가 만료·형식 오류 토큰에 401을 주는가. 500을 준다면 백엔드 수정 일정을 먼저 잡는다
- 401 재시도에서 뺄 경로 목록. 로그인, 소셜 로그인 콜백처럼 재발급으로 복구되지 않는 401
- 백엔드가 쿠키를 추가·변경할 때 BFF 변경을 같은 배포에 넣는 절차
- 파일 업로드와 스트리밍 경로를 BFF로 통과시킬지, 예외로 둘지
- CSRF 대응([1편](/posts/frontend-bff/bff-security-review))과 개발 환경 전용 디버깅 헤더([2편](/posts/frontend-bff/bff-poc-structure))

사내 적용이 끝나면, 이 목록 중 실제로 무엇이 문제가 됐는지 이어서 적겠습니다.
