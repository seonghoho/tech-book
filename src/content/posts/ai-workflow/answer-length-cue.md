# AI가 만든 문제은행에서 "가장 긴 보기가 정답" 단서 줄이기

## 만들고 있는 것

passedu는 SQLD, ADsP, 빅데이터분석기사(빅분기) 필기를 준비하는 사람을 위한 문제은행입니다. 서버 없이 브라우저에서만 동작하는 정적 사이트이고, 문항은 JSON 파일로 관리합니다. 문항 초안은 Claude로 만들었고, 다른 모델로 교차 풀이를 하거나 지표로 재는 방식으로 품질을 확인하고 있습니다.

지금 활성 문항은 SQLD 412개, ADsP 492개, 빅분기 필기 880개입니다.

## 문제: 긴 보기를 고르면 맞는다

객관식 문제를 많이 풀어 본 사람은 아는 요령이 있습니다. 잘 모르겠으면 가장 길고 자세한 보기를 고르는 것입니다. 출제자가 정답에는 조건과 설명을 꼼꼼하게 붙이고 오답은 대충 쓰는 경우가 많아서입니다.

AI로 만든 문항에서도 같은 경향이 보였습니다. 정답 보기에는 단서와 예외를 정확히 적다 보니 길어지고, 오답 보기는 짧은 한 줄로 끝나는 식이었습니다.

문제은행에서 이건 꽤 큰 문제입니다. 내용을 몰라도 긴 보기만 고르면 점수가 나오니, 연습 점수와 이 점수를 바탕으로 한 예상 점수가 실제 실력보다 높게 나옵니다.

## 재는 방법

문항마다 정답 보기의 글자 수를 가장 긴 오답 보기의 글자 수로 나눴습니다.

```ts
/** Correct choice length divided by the longest other choice. 1.3 means 30% longer than any distractor. */
export function answerLengthRatio(q: CueQuestion): number {
  const answer = q.choices.find((c) => c.id === q.answer);
  if (!answer) throw new Error(`정답 보기를 찾을 수 없습니다: ${q.id}`);
  const others = q.choices.filter((c) => c.id !== q.answer).map((c) => [...c.text].length);
  return [...answer.text].length / Math.max(1, ...others);
}
```

글자 수는 `[...text].length`로 셉니다. `text.length`는 UTF-16 코드 단위를 세서 이모지나 일부 문자가 두 개로 잡히기 때문입니다.

이 비율로 네 가지 지표를 봤습니다.

| 지표 | 뜻 |
|---|---|
| 정답이 가장 긴 보기인 비율 | 비율이 1보다 큰 문항의 비율 |
| 1.3배 이상인 문항 수 | 정답이 가장 긴 오답보다 30% 넘게 길어 눈에 띄는 문항 |
| 긍정형 문항에서 정답이 가장 긴 비율 | "옳은 것은?" 문항만 센 값 |
| 정답이 가장 짧은 보기인 비율 | 너무 고쳐서 반대 단서가 생기지 않았는지 보는 값 |

긍정형 문항을 따로 센 데는 이유가 있습니다. "옳지 않은 것은?" 같은 부정형 문항에서는 정답이 틀린 문장이라 길게 쓸 이유가 적습니다. 긴 보기 단서는 주로 긍정형 문항에서 생기기 때문에, 전체 평균만 보면 부정형 문항에 가려 작아 보입니다.

## 처음 잰 결과

2026년 11월 18일에 처음 쟀을 때 빅분기 필기가 가장 심했습니다.

| 시험 | 정답이 가장 긴 보기 | 1.3배 이상 |
|---|---|---|
| SQLD | 13% | 13문항 (4%) |
| ADsP | 23% | 21문항 (7%) |
| 빅분기 필기 | 35% | 91문항 (18%) |

빅분기 필기에서 긍정형 문항만 보면 48%였습니다. 긍정형 문항 두 개 중 하나는 가장 긴 보기를 고르면 맞는 상태였습니다.

## 고친 방법

### 오답을 정답만큼 구체적으로

빅분기 필기 91문항은 오답 보기를 정답만큼 구체적으로 다시 쓰거나, 정답 보기의 군더더기를 줄였습니다. 정답 기호, 문제 문장, 각 보기가 참인지 거짓인지는 그대로 두었습니다. 바꾼 오답 보기마다 왜 틀렸는지 설명하는 "오답 이유"도 새로 썼습니다.

보기 문장 초안은 Claude 하위 작업 4개가 과목별로 나눠 썼습니다. 다시 쓴 오답이 너무 그럴듯해져 정답이 둘로 읽힐 수 있는 곳이 4군데 있었고, 이 부분은 검토해서 고쳤습니다.

같은 날 ADsP 32문항도 고쳤습니다. 1.3배 이상인 21문항과, 긍정형이면서 1.15배 이상인 문항을 합친 수입니다.

### SQLD는 하나씩 보고 9문항만

SQLD는 모든 지표가 무작위 수준이었지만, 1.3배 이상인 13문항을 하나씩 봤습니다. 9문항은 실제로 문장 길이가 단서였고, 나머지 4문항은 숫자 자릿수나 SQL 명령어 이름 길이에서 생긴 차이였습니다. 보기가 `DELETE`, `TRUNCATE`, `DROP`, `ALTER`인 문항이라면 정답이 `TRUNCATE`일 때 가장 길 수밖에 없습니다. 이 4문항은 그대로 두었습니다.

### 보기를 바꾸면 새 ID로

passedu는 문항 수정 규칙을 둘로 나눕니다. 오타나 해설만 고치면 ID를 그대로 두고 `rev`를 올리고, 정답이나 보기가 바뀌면 새 ID를 줍니다. 학습자의 풀이 기록이 문항 ID에 묶여 있어서, 옛 문항을 지우지 않고 남겨 기록을 보존하기 위해서입니다. 은퇴한 문항은 오답 노트에서 숨깁니다.

그래서 고친 132문항(빅분기 91, ADsP 32, SQLD 9)은 모두 새 ID로 다시 내고 옛 ID는 `retired: true`로 남겼습니다. 개념 노트에서 대표 문항으로 걸어 둔 참조 24곳도 새 ID로 바꿨습니다.

### 테스트로 막는다

다시 생기지 않도록 문제은행 전체를 재는 테스트를 넣었습니다.

```ts
for (const exam of ['sqld', 'adsp', 'bigdata']) {
  it(`${exam} stays near chance`, () => {
    const dir = `content/questions/${exam}`;
    const questions = readdirSync(dir).flatMap((f) => JSON.parse(readFileSync(`${dir}/${f}`, 'utf-8')));
    const report = answerLengthCue(questions);
    expect(report.longest / report.total).toBeLessThanOrEqual(0.25);
    expect(report.strong.length / report.total).toBeLessThanOrEqual(0.1);
    // Positive stems are where "pick the longest" pays off; chance is about 25%.
    expect(report.positive.longest / report.positive.total).toBeLessThanOrEqual(0.3);
    // Overcorrecting must not create the reverse cue ("pick the shortest").
    expect(report.shortest.answer / report.shortest.total).toBeLessThanOrEqual(0.3);
  });
}
```

마지막 조건은 고치면서 추가했습니다. 정답을 줄이고 오답을 늘리다 보면 이번에는 "가장 짧은 보기가 정답"이라는 반대 단서가 생길 수 있습니다. 그래서 두 방향을 같이 봅니다.

CI가 main에 push될 때마다 빌드 전에 테스트를 돌리므로, AI로 문항을 추가하다 단서가 다시 늘면 배포 전에 실패합니다.

## 지금 수치

이 글을 쓰면서 지금 문제은행으로 다시 쟀습니다. 그사이 빅분기 필기는 부정형 문항 보강 등으로 문항이 크게 늘었습니다.

![정답이 가장 긴 보기인 문항 비율. 빅분기 필기는 35%에서 21%를 거쳐 지금 13.5%, ADsP는 23%에서 16%를 거쳐 13%, SQLD는 13%에서 12%를 거쳐 10.4%다. 세 시험 모두 지금 값이 무작위 기대(16.8%, 17%, 13%)보다 낮다](/images/posts/ai-workflow/answer-length-cue/longest-answer-share.png)

| 시험 (활성 문항) | 정답이 가장 긴 보기 | 무작위 기대 | 1.3배 이상 | 긍정형에서 가장 긴 보기 | 정답이 가장 짧은 보기 |
|---|---|---|---|---|---|
| SQLD (412) | 10.4% | 13.0% | 5문항 | 13.7% | 14.7% |
| ADsP (492) | 13.0% | 17.0% | 0문항 | 19.9% | 16.8% |
| 빅분기 필기 (880) | 13.5% | 16.8% | 0문항 | 24.6% | 16.1% |

"무작위 기대"는 문항마다 보기 하나를 무작위로 골랐을 때 그 보기가 유일하게 가장 긴 보기일 확률을 평균한 값입니다. 길이가 같은 보기가 여럿이면 가장 긴 보기가 정해지지 않으니 0으로 셌습니다. 세 시험 모두 지금 값이 이 기대보다 낮습니다. 긴 보기를 고르는 요령은 이제 통하지 않습니다.

테스트 9개도 모두 통과합니다.

## 다른 방법

| 방법 | 효과 | 한계 |
|---|---|---|
| 보기 순서를 섞는다 | 정답 위치 단서는 없어진다 | 길이 단서는 그대로 남는다 |
| 생성할 때부터 보기 길이를 맞추라고 지시한다 | 처음부터 단서가 덜 생긴다 | 지시만으로 지켜지는지는 결국 재 봐야 한다 |
| 모든 보기를 비슷한 길이로 늘린다 | 길이 차이가 줄어든다 | 오답에 의미 없는 말이 붙어 다른 단서가 생길 수 있다 |
| 오답을 구체적으로 다시 쓰고, 지표와 테스트로 막는다 (이번 방법) | 내용이 있는 오답이 되고, 다시 생기면 테스트가 잡는다 | 문항마다 오답 이유를 다시 써야 하고, 사람 검수가 필요하다 |

객관식 문항 작성 지침을 정리한 Haladyna, Downing, Rodriguez(2002)의 논문에도 "보기 길이를 비슷하게 맞추라"는 항목이 있습니다. 사람이 쓴 문제에서도 오래전부터 알려진 단서입니다. AI로 문항을 대량으로 만들면 이 단서도 같이 대량으로 생기기 때문에, 사람이 눈으로 보기 전에 지표로 먼저 거르는 쪽이 현실적이었습니다.

## 비슷한 문제를 알아보는 법

AI로 객관식 문제를 만든다면 아래를 재 보면 좋습니다.

- 정답이 가장 긴 보기인 비율이 무작위 기대보다 높다
- 긍정형 문항만 따로 보면 그 비율이 더 높다
- 정답이 가장 긴 오답보다 30% 넘게 긴 문항이 많다
- 반대로, 고친 뒤 정답이 가장 짧은 보기인 비율이 올라갔다

길이 단서 말고도 비슷한 단서가 있습니다. 정답 보기에만 "일반적으로", "경우에 따라" 같은 조심스러운 표현이 붙거나, 정답 보기만 문제 문장과 같은 단어를 반복하는 경우입니다. 이런 단서도 같은 방식으로 셀 수 있습니다.

## 남은 것

- 고친 문항은 모두 운영자 검수 전입니다. 새 오답이 정답처럼 읽히지 않는지, 줄인 정답이 뜻을 잃지 않았는지 사람이 봐야 합니다.
- SQLD의 1.3배 이상 문항은 지금 5개입니다. 4개는 위에서 남겨 둔 명령어 이름·숫자 문항이고, 나머지 1개(sqld-1-0092)는 그 뒤 들어온 문항으로 정답 보기만 이유까지 붙은 실제 문장 길이 단서였습니다. 테스트 기준(10%) 안이라 통과했지만 다시 써야 합니다. 비율 기준만으로는 이런 한두 문항을 놓칠 수 있어서, 1.3배 이상 목록은 주기적으로 눈으로 보는 게 좋겠습니다.
