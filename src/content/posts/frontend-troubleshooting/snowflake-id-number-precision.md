# Snowflake ID를 숫자로 받으면 게시글이 전부 404가 되는 이유

## 아직 터지지 않은 버그

사이드 프로젝트의 커뮤니티 기능을 점검하던 중이었습니다. 백엔드가 며칠 전에 응답의 식별자 타입을 `long`에서 `String`으로 바꿨는데, 프론트엔드는 여전히 게시글 ID를 숫자로 다루고 있었습니다.

처음에는 타입만 맞추면 되는 문제로 보였습니다. 실제로 따라가 보니 타입 불일치 수준이 아니었습니다. 실제 게시글이 하나라도 생기면 상세 페이지가 전부 404가 되는 상태였습니다. 개발 서버의 커뮤니티에 글이 0건이라 아직 터지지 않았을 뿐이었습니다.

## 원인: Number가 정확히 표현할 수 있는 정수에는 한계가 있다

게시글, 댓글, 회원 ID는 Snowflake 방식으로 발급됩니다. 발급 시각을 비트로 밀어 넣어 만드는 64비트 정수라서, 이 프로젝트에서는 약 7.5×10¹⁷ 크기였습니다.

JavaScript의 `Number`는 64비트 부동소수점입니다. 정수를 빠짐없이 정확하게 표현할 수 있는 범위는 `Number.MAX_SAFE_INTEGER`, 약 9.0×10¹⁵까지입니다. Snowflake ID는 이 범위를 두 자릿수나 넘습니다.

```js
Number.MAX_SAFE_INTEGER // 9007199254740991 (약 9.0e15)

const id = "751234567890123456" // 약 7.5e17
Number(id)                      // 751234567890123500 — 뒷자리가 바뀜
Number.isSafeInteger(Number(id)) // false
String(Number(id)) === id        // false
```

이 범위를 넘는 정수는 가장 가까운 표현 가능한 값으로 바뀝니다. 서로 다른 ID가 같은 숫자가 되기도 합니다.

```js
Number("751234567890123456") === Number("751234567890123457") // true
```

## 상세 페이지가 404가 되는 흐름

프론트엔드의 상세 페이지는 URL의 ID를 이렇게 검사하고 있었습니다.

```ts
// 수정 전
export const parseCommunityPostId = (value: string | null) => {
  if (!value || !/^[1-9]\d*$/.test(value)) {
    return null
  }

  const postId = Number(value)
  return Number.isSafeInteger(postId) ? postId : null
}

// 상세 라우트 (단순화)
const postId = parseCommunityPostId(params.communityId)
if (postId === null) notFound()
```

숫자 형태인지 확인한 뒤, 숫자로 바꿔서 안전 정수인지 한 번 더 보는 검사였습니다. 그런데 Snowflake ID는 처음부터 안전 정수 범위 밖이라, `Number.isSafeInteger`가 항상 `false`를 돌려줍니다.

```
'751234567890123456'
  → Number()            → 751234567890123500 (isSafeInteger: false)
  → parseCommunityPostId → null
  → notFound()          → 404
```

이 검사는 정상적인 실제 ID를 모두 잘못된 ID로 판단하고 있었습니다. 테스트에도 "안전 정수를 넘으면 잘못된 형태"라는 전제가 들어가 있었는데, 그 전제가 틀린 것이었습니다.

## 같이 숨어 있던 버그 두 개

ID를 숫자로 다루는 코드를 찾아보니 두 군데가 더 있었습니다.

**1. 본인 글인데도 수정·삭제 버튼이 안 뜸**

글쓴이 본인인지 확인하는 함수가 숫자로 바뀐 게시글 작성자 ID를 `String()`으로 되돌려 세션의 회원 ID와 비교하고 있었습니다. 한 번 뒷자리가 바뀐 숫자는 원래 문자열로 돌아오지 않습니다. 그래서 본인 글에서도 항상 `false`가 나와, 수정·삭제 버튼이 보이지 않았습니다.

**2. SEO 메타데이터가 조용히 기본값으로 떨어짐**

서버에서 게시글 응답을 검사하는 타입 가드가 `postId`를 `number`로 요구하고 있었습니다. 백엔드가 문자열로 보내기 시작한 뒤로는 실제 응답이 전부 이 검사에서 탈락했습니다. 오류는 나지 않고, 게시글 페이지의 제목과 설명 메타데이터가 사이트 기본값으로 대체되고 있었습니다.

둘 다 에러 없이 조용히 잘못 동작하는 버그였습니다. 숫자로 바뀐 ID는 예외를 던지지 않고 다른 값이 되기 때문에, 화면에 문제가 드러나기 전까지 알아채기 어렵습니다.

## 수정

**ID 타입을 한 곳에서 정의했습니다.**

```ts
/**
 * 게시글·댓글·회원 id는 Snowflake라 약 7.5e17이고,
 * Number.MAX_SAFE_INTEGER(약 9.0e15)를 넘는다.
 * 숫자로 파싱하면 뒷자리가 조용히 바뀌어 서로 다른 글이 같은 id로 보인다.
 */
export type CommunityId = string
```

왜 문자열인지, 어디서 `Number()`를 쓰면 안 되는지를 이 타입 옆에 적어 두었습니다. 게시글, 댓글, 작성자 ID가 모두 이 타입을 씁니다.

**ID 검사는 숫자로 바꾸지 않고 형태만 봅니다.**

```ts
// 수정 후
export const parseCommunityPostId = (value: string | null): string | null =>
  value && /^[1-9]\d*$/.test(value) ? value : null
```

자릿수 상한은 두지 않았습니다. Snowflake ID는 시간이 지날수록 커지는데, 상한을 두면 언젠가 이번과 같은 방식으로 정상 ID를 조용히 막게 됩니다.

**정렬과 커서 비교는 BigInt로 바꿨습니다.**

목 데이터에서 ID 순으로 정렬하거나 커서와 비교하는 코드가 있었습니다. 문자열을 그대로 비교하면 사전순이라 자릿수가 다를 때 틀립니다.

```js
["9", "10"].sort()                          // ["10", "9"] — 틀림
[9n, 10n].sort((a, b) => (a < b ? -1 : 1)) // [9n, 10n]
```

ID를 비교할 때는 `BigInt(id)`로 바꿔서 비교했습니다. 두 화면에 각각 리터럴 `0`으로 흩어져 있던 첫 페이지 커서 값도 상수 하나로 모았습니다.

## 요청 보낼 때 남은 문제

응답은 백엔드가 문자열로 바꿔 줬지만, 요청 쪽은 아직 `long`으로 받는 곳이 남아 있었습니다.

| 위치 | 상태 |
|---|---|
| URL 경로·쿼리 | 문자열을 그대로 URL에 넣으므로 안전. JS 숫자를 거치지 않음 |
| 요청 본문의 `parentCommentId`, `targetId` | 문자열로 보내고, 백엔드(Jackson)가 문자열을 숫자로 바꿔 주는 동작에 기댐 |

요청 본문에서 `Number(id)`를 쓰는 순간 그게 바로 정밀도 손실입니다. 그래서 프론트에서는 문자열로만 보내고, 요청 쪽도 백엔드가 문자열로 받도록 바꾸는 일은 후속 작업으로 남겼습니다.

## 먼저 겪었던 북마크 ID

사실 같은 문제를 북마크 ID에서 먼저 겪었습니다. 그때는 백엔드가 아직 북마크 ID를 숫자로 내려주고 있어서, 프론트에서 우회해야 했습니다.

`JSON.parse`는 큰 숫자를 읽는 순간 정밀도를 잃습니다.

```js
JSON.parse('{"bookmarkId":751234567890123456}').bookmarkId
// 751234567890123500
```

그래서 북마크 API만 응답을 파싱하기 전에 원문 JSON에서 `bookmarkId` 숫자를 정규식으로 찾아 따옴표로 감싸는 변환을 넣었습니다. 망가진 ID로 삭제 요청을 보내면 없는 북마크를 지우거나, 최악의 경우 다른 사람의 북마크를 가리킬 수 있었기 때문입니다.

백엔드가 북마크 ID를 문자열로 바꾼 뒤에 이 우회를 걷어냈습니다. 이때 순서를 지켰습니다. 저장소의 백엔드 코드만 보고 지우지 않고, 개발 서버에 실제로 배포된 API 문서(OpenAPI)에서 `bookmarkId`가 `type: string`인 것을 확인한 뒤에 지웠습니다. 배포 전에 우회를 먼저 지우면, 그 사이에 다시 ID가 망가집니다.

## 놓친 이유

이 프로젝트에는 응답 스키마를 고정해 두고 타입을 맞추는 테스트가 있었습니다. 하지만 프론트 쪽에 고정한 값끼리 비교하는 구조라, 백엔드가 타입을 바꾼 것은 잡지 못했습니다. 실제로 이번에 놓친 경로였습니다. 그 테스트에 "이 검사는 백엔드 변경을 잡지 못한다"는 한계를 적어 두고, Snowflake 크기의 ID로 상세 페이지를 여는 회귀 테스트를 추가했습니다.

64비트 정수 ID를 쓰는 백엔드와 일한다면, 응답을 받는 첫 지점부터 ID를 문자열로 다루는 게 가장 단순합니다. 숫자로 한 번이라도 바뀌면 되돌릴 방법이 없습니다.
