# 프론트엔드 BFF 연재 계획

블로그에 BFF 연재(4편)를 쓰기 위한 계획과 재료다. 다른 PC에서 이어서 쓸 수 있도록 조사한 사실을 이 문서에 모았다.

## 결정한 것

- 4편으로 나눈다. 3·4편을 합친 3부작보다 사례가 하나씩 검색되기 좋다.
- 카테고리 폴더 `src/content/posts/frontend-bff/`를 새로 만들고, `src/lib/categoryMap.ts`에 라벨(예: `"frontend-bff": "Frontend BFF"`)을 추가한다.
- 프로젝트 이름, 날짜, 동료 이름, API 도메인은 쓰지 않는다. "사이드 프로젝트", "첫 번째 프로젝트 / 두 번째 프로젝트"로 쓴다. 회사 업무 프로젝트는 소재로 쓰지 않는다.
- 1편(개념)은 일반론이 되지 않도록, 개념마다 실제 구조의 예시를 붙인다.
- 한 편씩 발행하고, 편마다 앞뒤 편 링크를 건다.
- 말투는 메모리의 blog-writing-tone 규칙을 따른다(슬로건형 소제목, "A가 아니라 B", 근거 없는 "안정적으로", 교훈형 마무리, 첫째/둘째/셋째 금지). 합니다체.

## 진행 방식

1. 1·2편은 개념과 아래 사실로 Claude가 초안을 먼저 쓴다. 개념 설명의 사실(BFF 패턴의 유래 등)은 출처를 확인해서 넣는다.
2. 3·4편은 아래 인터뷰 질문의 답을 받아 쓴다. 1·2편 검토 때 같이 받는다.
3. 이미지는 사용자가 캡처하고, 가릴 부분은 Claude가 가리고 잘라서 `public/images/posts/frontend-bff/<slug>/`에 넣는다. 이미지가 없으면 흐름 다이어그램으로 대신한다.

## 편별 구성

| 편 | 제목(가안) | 내용 |
|---|---|---|
| 1 | BFF란 무엇인가 | 정의, 처음 나온 배경, API Gateway와의 차이, Next.js Route Handler로 만드는 형태. 예시는 브라우저 → Next 서버 → 백엔드 흐름 |

| 3 | 사이드 프로젝트에 BFF를 넣은 과정 | 첫 번째 프로젝트의 인증 BFF, 두 번째 프로젝트에서 이 구조를 근거로 채택·확장, Claude Code와 명세 → 계획 → 구현으로 진행한 방식 |
| 4 | BFF를 운영하며 만난 문제들 | 만료 토큰에 500, 로그인 실패 재시도로 계정 잠금, multipart 깨짐, SSE 버퍼링, 리뷰 지적을 실행해서 확인한 일 |

## 조사한 사실

두 사이드 프로젝트는 같은 백엔드 구조(게이트웨이 + JWT)를 쓴다. 커밋, 명세, 인계 문서에서 확인한 내용이다.

### 첫 번째 프로젝트: 인증 BFF 도입

- 도입 이유: 기존 axios 래퍼가 accessToken을 localStorage와 쿠키에 보관하고, 401 갱신도 클라이언트가 했다. XSS 노출을 없애고, 클라이언트에 흩어진 갱신 로직을 걷어내려고 했다.
- 진행: 명세(`docs/features/auth/session-bff.md`)와 구현 계획을 먼저 쓰고, 계획서 첫 줄에서 subagent-driven-development를 지시했다. 구현 PR 하나에 71개 파일, +4543/-1745.
- 구조
  - 토큰을 jose JWE로 암호화한 HttpOnly 세션 쿠키에 봉인
  - `/api/auth/login`, `logout`, `me` 라우트
  - `app/api/bff/[...path]/route.ts` catch-all이 Bearer를 붙이고, 401이면 한 번 재발급 후 재시도
  - `/api/v1` prefix 자동 부착, 브라우저가 보낸 Authorization 헤더는 버림
  - 로그인 후 이동 경로(safeRedirect)의 백슬래시 open-redirect 우회 차단
- route.ts 크기: 142줄

### 두 번째 프로젝트: 같은 구조를 가져와 확장

- 기반 명세(fe-foundation-spec)에서 BFF 채택을 권고했다. 근거:
  - access token이 응답 body로 온다
  - refresh 쿠키가 `HttpOnly; SameSite=Strict; Path=/api/v1/auth/token/reissue`라 브라우저가 직접 다룰 수 없다
  - 외부 API 키를 서버에서 넣을 수 있다
  - 첫 번째 프로젝트가 같은 백엔드 구조로 `/api/bff`를 운영 중이다
- 구조
  - AES-256-GCM 봉인 쿠키, 응답 body에서 토큰 필드 제거
  - 401이면 한 번 재발급, env는 zod로 검증
  - 서버 컴포넌트는 BFF를 거치지 않고 게이트웨이를 직접 호출(전송 계층 2개: 브라우저용 client, 서버용 server)
  - Next 16에서 `middleware.ts` → `proxy.ts`
  - 헤더를 화이트리스트로 다시 구성해서 Origin이 붙지 않음 → FE dev 포트가 백엔드 CORS 허용 목록과 무관해짐. 헤더를 그대로 넘기도록 "개선"하면 POST만 빈 403이 나는 함정이 있어 리뷰 항목으로 추가
  - 게이트웨이가 꺼져 있을 때 빈 500 → 503 + 공통 응답 래퍼(`bff-error.ts`)
- route.ts 크기: 451줄

### 운영하며 만난 문제 (4편 재료)

- 만료 토큰에 500
  - 백엔드가 만료 토큰에 401이 아닌 500을 돌려줘서 재발급이 일어나지 않았다. 만료 토큰을 가진 사용자는 공개 API까지 500을 받았다.
  - 첫 번째 프로젝트: 프론트에서 우회. JWT `exp`를 보고 미리 재발급하고(single-flight로 동시 요청 8건이어도 재발급 1회), 재발급까지 실패하면 익명으로 전달. 테스트 786/786, 만료 쿠키로 요청 시 500 → 200.
  - 두 번째 프로젝트: 백엔드 게이트웨이에서 JWT 예외를 401/503 응답으로 바꾸는 근본 수정.
  - 같은 원인을 프론트 우회와 백엔드 수정으로 각각 푼 비교 사례.
- 로그인 실패를 토큰 만료로 오인
  - 로그인 실패 401도 재발급 후 재시도해서, 실패가 2번씩 세어졌다. 계정 잠금이 절반의 시도 만에 걸렸다.
  - 인증 진입 경로(로그인 등)는 재시도 대상에서 뺐다.
- multipart 업로드
  - 요청 본문을 `request.text()`로 읽고 Content-Type을 JSON으로 고정해서 boundary와 바이너리가 깨졌다.
  - 원본 Content-Type을 보존하고 ArrayBuffer로 읽도록 고쳤다. 401 재시도 때 같은 본문을 다시 보내야 해서 스트림이 아닌 버퍼로 들고 있는다(`forwarded-body.ts`).
  - 병렬 작업을 나누기 전에 이 수정을 공통 선행 작업으로 먼저 올렸다.
- SSE 버퍼링
  - route.ts가 `await response.text()`로 응답 전체를 기다려서, 이벤트가 작업이 끝난 뒤 한꺼번에 왔다.
  - 요청의 `Accept: text/event-stream` 완전 일치로 SSE를 판정(응답 헤더로 판정하면 이미 늦고, BFF가 고정으로 넣던 Accept 때문에 406이 났다).
  - SSE 경로만 토큰 필드 제거를 건너뛴다. `X-Accel-Buffering: no`, `request.signal` 전달로 연결 정리, 401 재시도는 스트림 시작 전에만.
  - 계약 함정: 이벤트 이름이 `job-update`라 `onmessage`로 오지 않음, data에 공통 래퍼 없음, 종료 후 EventSource 자동 재연결 루프.
  - 늦게 온 폴링 응답이 완료 상태를 되돌리지 않도록 병합 함수를 두고, 반쯤 열린 연결에 대비해 30초 안전 폴링을 남겼다.
  - SSE 전후의 지연 수치는 측정하지 않았다.
- 소셜 로그인 state 쿠키
  - 게이트웨이 쿠키의 `Path=/api/v1/auth`가 브라우저에 보이는 `/api/bff/...` 경로와 달라 그대로 통과시킬 수 없었다. BFF가 쿠키를 중계하도록 바꿨다.
- 로그인 후 원래 페이지로 돌아가지 않던 버그
  - 원인은 Next route cache였고 `location.replace`로 해결했다. BFF 인증 흐름 전체를 바꾸는 대안은 버렸다.

### Claude Code와 작업한 방식 (3·4편 재료)

- 명세와 계획을 먼저 쓰고, 서브에이전트가 태스크별로 구현하고, 태스크마다 리뷰했다. 미리 재발급 작업은 태스크 3개, 최종 리뷰 APPROVE.
- SSE 작업에서 리뷰 서브에이전트가 "검증되지 않았으니 스트림 401 재발급 분기를 지우자"고 했다. 가짜 게이트웨이로 실행해 보니 만료 토큰 → 401 → 재발급 → 200, Set-Cookie도 스트리밍 응답과 함께 나갔다. 지적을 받지 않았다.
- 리뷰가 실제로 잡은 것: EventSource URL 조립이 계층 규약 위반(린트 규칙 `noDirectFetch`가 EventSource를 못 봄), 문서끼리 설명이 다름, 토큰 필드 제거 예외가 문서에 없음.
- AI가 원인을 잘못 짚은 일: "dev 서버가 안 뜬다"를 pnpm·포트 문제로 진단했지만, 실제로는 프리뷰 프로세스가 샌드박스 권한(EPERM)에 막힌 것이었다. 그 사이 FE PR 여러 건이 실제 화면 확인 없이 머지됐다.
- 백엔드가 로컬에서 뜨지 않아서 mock SSE, echo/스텁 게이트웨이로 검증했다.
- e2e는 BFF 호출을 `page.route` 고정 응답으로 대신한다.

## 캡처하면 좋은 화면

- 개발자 도구 Network 탭에서 `/api/bff/...` 요청이 보이는 화면
- Application 탭에서 HttpOnly 세션 쿠키가 보이는 화면(값은 가린다)
- 없으면 브라우저 → BFF → 게이트웨이 흐름을 다이어그램으로 그린다
